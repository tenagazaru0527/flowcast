## 2. 有効な決定

### 2-1. 構想レベル

| 決定 | 理由 | 差し戻し条件 |
|---|---|---|
| 入力は「線」のみ。発生源・目的地はシステム側 | 流動デザインに最短。点をプレイヤー入力にすると配置ゲーに寄る | — |
| 線の入力形式は (b) ノード間接続 | 因果の説明可能性を優先 | 将来 (d) 制御点簡約へ差し替え検討 |
| 実行中の線変更は禁止（一時停止のみ許可） | 観賞型の骨格を保つため | — |
| リプレイ外部共有を行う | ← これが決定論要件（整数演算化）の根拠 | 共有を諦めるなら決定論要件を緩められる |
| リプレイ方式は seed + 入力の再計算。イベント記録は事後分析UI用に別途 | — | — |
| 初回実装スコープはテーマ非依存の検証のみ | — | PoC-0 通過後 |

### 2-2. 決定論の要件

- 全数値 32bit 整数、小数は Q16.16 固定小数点
- 乗算は `((a * b) / 65536) | 0`。**`>> 16` は 32bit 切り詰めのため使用不可**
- `Math.random` / `Date.now` / `performance.now` 禁止
- `Math.sqrt` / `sin` / `cos` / `pow` 等の浮動小数点関数 禁止（`Math.imul` / `Math.abs` は可）
- 乱数は単一 seed の xorshift32 のみ
- `Map` / `Set` / `for...in` のイテレーション順に依存しない
- 場の更新はダブルバッファ方式
- 固定タイムステップ（3600ステップ）
- 平方根が必要な場合は `isqrt`（ビット単位法・厳密値）を使う

**検証手段**: `scripts/check-forbidden-apis.js`（`src/` 限定）と
`scripts/check-runtime-hashes.js`。CI で Node 20/22 マトリクス実行。

### 2-3. 指標と基準

| 決定 | 理由 |
|---|---|
| 基準2・3 の判定指標は **completionRatio**（生値の整数比） | `completionStep` は崖端指標。3%変位で10件中8件が未到達となり測定が成立しなかった |
| 基準3 は 1% / 3% / 10% の3水準。単調性 + 10%が1%の3.0倍以上 | 旧定義（10%で15%以上変化）は偽陽性。1%で13.4%、10%で15%＝ノイズ床を測っていた |
| 基準2 は9/10以上がPASS。Step 4の報告では数値のみで合否判定が抜けていた | adv:diff = 1:1 は9/10でPASS |
| adv:diff = 1:1 は基準1・2・3がPASSし、基準4のみFAIL | occupiedPeakは4,037〜4,090で、数値基準が最も通る領域に見るべき流れが存在しない |
| `densityMax` は輻輳指標として使わない | 総流出予算が density 比例のため、source 密度は下流に依存しない source 平衡値である |
| 輻輳指標は `densityMaxExSource`（全sourceセルと各マンハッタン距離1近傍の和集合を除外） | — |
| `completionAuc` は導入しない | completionRatio が平坦でなかったため、保険を使う条件が成立しなかった |
| **基準の閾値は変更しない** | 基準を通すための調整を構造的に禁じる |
| 掃引ハーネスは判定・順位付け・推奨を行わない | 自動探索が基準を通す方向に走ると、上記の禁止が機械的に破られる |
| 長い迂回経路の崩壊原因は、guideが線方向のみで線へ戻る成分を持たないこと | Step 7でdetourはギャップ通過後に場外へ散った。ギャップ幅・流量上限ではなく経路長耐性の問題として扱う |
| Node 22 の決定性確認は CI の Node 20/22 マトリクスに任せ、ローカルは Node 20 のゼロ依存構成を維持する | CI が毎 push 実行するため、ローカル固定Nodeが短縮するのは取得待ちのみ。一方で依存追加は Vanilla JS・ビルド工程なし・外部ライブラリ不可という前提を損なう |

### 2-4. 実装方針

| 決定 | 理由 |
|---|---|
| `measure: true` 分岐内に限り計装を追加してよい | measure=false/true でハッシュが一致することを実測済み。「src/ を変更しない」制約はハッシュ不変を守る手段であって目的ではない |
| `maxStagnation` の定義は変更しない | 実験の途中で既存指標の意味を変えない。流量上限の効果は `fluxLimitedAmount` で見る |
| 微細最適化は実施しない | GC 4.62%、neighborIndex 0.17%。全施策を積んでも3〜4割。並列化は8〜10倍でモデルに触れない |
| engineVersion を上げたら同一コミットで `runtime-hashes.json` に記録 | 記録がなければ CI が FAIL する（Step 0.4 でゲート強化済み） |
| 1周1変更 | 原因帰属のため。clamp 修正と流量上限を同時に入れると効果を切り分けられない |
| `poc-1-wide` の既定はsource幅1・sink幅5 | source幅9は線3本のため注入の67%が無誘導。sink幅1は正常なビーム移動を当たり／外れに二値化した。基準値から独立に確認された構造的欠陥を除去し、sink幅は後で狭められる安全側の5とした |
| 線は障害物セルにも通常どおり焼き込む | 障害物セルのguideは移送で参照されない。焼き込みを除外して障害物の縁に新しい不連続を作る必要がない |
| 線を純粋なポテンシャル場へ全面置換せず、既存guideへ障害物を越えない距離場の復元力を加算する | 全面置換案では旧挙動を機械的に証明できない。`restoreWeight=0` で0.7.0の全9ハッシュを保存したまま、線から外れた材料だけを戻せる |
| guide の定式化は復元力の加算方式で決着とする | Step 8で静的BFS距離場の最急降下方向を既存guideへ加算し、障害物を越える復元を避けつつ後方互換を証明できた |
| 混雑基準は `congestionReference` としてcapacityから分離し、通気度はadvectionScoreだけへ乗算する | capacityとreverseThresholdの依存を崩さず、diffusionによる混雑回避を残す |
| 密度場スナップショットを掃引成果物としてcommitする | 掃引CSVはスカラーのみのため、数値の64×64密度場も保存する |
| 通気度（Step 9）は残す | 自己調整は戻らなかったが、中央ルート比率の絶対値を28.0%→33.6%と動かし、完了率・場外損失を悪化させない |
| 漏れ防止は「力」ではなく「幾何制約」で担う | 復元力は漏れと自己調整の両方を同時に止める。制約なら経路選択の自由度を奪わない |
| 回廊制約は restoreWeight = 0 のときのみ機能する | 復元力が非ゼロだと材料が線を離れず、回廊が発動しない。掃引の対照群で cw=2・rw=Q/16 が Step 9 と同じ 0.12/0.17pt に留まることを確認 |
| 掃引の `gapWidth` は `{1, 3, 5, 9}` とする | 63 は障害物が生成されず、峡谷シナリオとして成立しない |
| 場外損失は配置依存の幾何に頼らず、設定で構造的に排除できるようにする | Step 10 では源・シンクと場の左右端との距離（4セル）だけで場外損失の有無が決まり、`corridorWidth >= 3` の評価が汚れた |
| `debug/` のビューアはエンジンの変更に追随させる | Step 7〜11 の5つの機構がビューアに反映されず、「見て面白いか」の判断が5回保留された |
| ビューアで任意の線を引けるようにする | `INPUTS` の3種のみでは、入力と出力の対応をプレイヤー視点で確かめられない |
| ビューアの盤面保存は `src/` の replay 形式を使わず、`debug/` 独自形式とする | `createReplay` は `scenarioId` を `poc-0-default` に固定しており、峡谷シナリオや任意パラメータを表現できない。`src/` 側を触らずに済ませる |
| **「見て面白いか」に初めて肯定的な判断が得られた** | Step 12のビューア操作で「今までになかった楽しさ」「流体シミュレータを自分で操作している感じ」「流れをコントロールしている感じ」と評価され、Step 7以降保留だった論点に操作体験から回答が出た |
| 曲線入力は `src/` の変更なしに実現できる | `burnLines` は制御点数に上限を持たず、1/4セル刻みでサンプリングする。制御点161個の事前実測でも実行時間は約3.6秒だった |
| ビューアの線はQ16.16で保持する | `assertPoint` は整数セルを要求せずQ16.16範囲を受け付ける。セル単位への丸めはビューア側だけの制限だった |
| **受け入れ基準4件は「エンジンが壊れていないことの確認」に位置づけを限定し、PoC-0 の通過条件としては扱わない** | 既定値を決めるための基準を遊ぶ前に固定する循環を避ける。エンジンの健全性は決定論・保存則・300点以上の掃引で別途確認済みであり、**閾値と既定値は変更せず、位置づけのみを変える** |
| **`debug/` は診断用ツールのままとする。ゲーム層は将来、別ディレクトリに新規で作る** | 境界線は`runSimulation`の入力を作る／出力を読むところまでとし、成功・失敗判定、スコア、演出、UIの作り込みは入れない |
| **盤面の幾何（障害物・源・シンク・ギャップ）は既にエンジンの自由な引数である** | `runSimulation`が引数で受け取っており、固定されているのは`src/scenarios.js`の定数側だけだった。柱・器・源とシンクの移動はいずれも`src/`の変更なしに可能 |
| **編集された盤面（`scenarioId = custom`）はハッシュ回帰テストの対象外とする** | 検証用シナリオ3件と編集盤面を同じ名前空間で混ぜず、`runtime-hashes.json`の対象を3件のまま固定する |
| 時系列の標本は measure 専用とし、既定 `sampleInterval = 0` で記録しない | 既存の全実行と `stateHash` を変えないため。時系列は診断と検討のための情報であり、シミュレーションの一部ではない |
| エンジンは累積値のみを記録し、区間量・変化率・判定は行わない | 掃引ハーネスが判定・順位付け・推奨を行わないのと同じ原則。加工は利用側で行う |
| 時系列は掃引 CSV に出力しない | 標本数が数十になり列数が爆発する。掃引の CSV 構成は変更しない |
| 「線と流路の一致度」はスカラーではなく、線からの距離別の密度分布として記録する | 回廊制約が材料を `corridorWidth` 以内に閉じ込めているため、「距離 d 以内の割合」は `d >= corridorWidth` で構造上ほぼ 100% になり、`d` の選び方が結論を決めてしまう。分布であれば定義を変えても再実行が不要 |
| 分布の記録に既存の BFS 距離場を再利用し、新しい場を作らない | Step 8 で導入し Step 10・11 で回廊判定に使っている距離場をそのまま使える。新しい概念を持ち込まない |
| 計測はスカラーへの加工・判定・比の算出を行わない | 掃引ハーネスが判定・順位付け・推奨を行わないのと同じ原則。加工は利用側で行う |
| シンクの内訳は `sinkGroups`（名前付きセル群）で表現し、`gaps` と同型とする | 既にある仕組みを流用し、新しい概念を持ち込まない |
| `sinkGroups` は `sink` 全体を過不足なく分割する | `Σ sinkThroughput === totalCompleted` が不変条件になり、実装誤りを検出できる。`gaps` と異なり部分集合は許さない |
| `sinkFirstArrivalStep` はしきい値を用いず、初めて到達量が0より大きくなったstepを記録する | しきい値が結論を決めることを避け、計測を事実の記録に限定する |
| ゲーム層を `game/` に新規で作る | Step 14 の決定（`debug/` は診断用のまま）に従う。`debug/` のコードを共有せず独立させる |
| 最初の課題は配分型とする | Step 17 で `sinkThroughput` が取得可能になった。到達順と配分の両方に流体の時間的性質が出る |
| 判定は順序付きとし、重み付き合算スコアを作らない | 単一量の最大化で「基準を最もよく満たす設定が画面として最も無価値」になる失敗を2回している |
| スコア軸は生の数値を並べるのみとし、順位付け・星の数などを付けない | 掃引ハーネスが判定・順位付け・推奨を行わないのと同じ原則 |
| 失敗時は落ちた条件と実測値を示し、助言や誘導の文言は入れない | 「次に線をどう変えるか」が想像できることが再挑戦の動機になる |
| CI をテストの種類ごとにジョブ分割する | Step 8 以降、ハッシュ回帰テストが1 Step ごとに1件ずつ増える構造であり、Step 17 で余裕19秒、Step 19 で超過した。実測ではハッシュ回帰群177秒・保存則138秒の2系統で全体437秒の72%を占め、残り25件は合計数秒だった |
| CI のタイムアウトを 10 分から 15 分へ延長する | 分割だけに頼ると、次にテストが増えたときに同じことが起きる。分割と延長の両方を行う |
| Node 20 / 22 のマトリクスは維持する | 決定論の検証がこのマトリクスに依存している（第2-3節） |
| テストは削除・スキップせず、分割のみとする | 時間短縮のためにテストを減らすと、決定論の検証範囲が狭まる |
