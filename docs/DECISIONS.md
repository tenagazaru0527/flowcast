## 2. 有効な決定

### 2-1. 構想レベル

| 決定 | 理由 | 差し戻し条件 |
|---|---|---|
| 入力は「線」のみ。発生源・目的地はシステム側 | 流動デザインに最短。点をプレイヤー入力にすると配置ゲーに寄る | — |
| 線の入力形式は (b) ノード間接続 | 因果の説明可能性を優先 | 将来 (d) 制御点簡約へ差し替え検討 |
| 実行中の線変更は禁止（一時停止のみ許可） | 観賞型の骨格を保つため | — |
| リプレイ外部共有を行う | ← これが決定論要件（整数演算化）の根拠 | 共有を諦めるなら決定論要件を緩められる |
| リプレイ方式は seed + 入力の再計算。イベント記録は事後分析UI用に別途 | — | — |
| 初回実装スコープはテーマ非依存の検証のみ | — | PoC-0 通過後 |

### 2-2. 決定論の要件

- 全数値 32bit 整数、小数は Q16.16 固定小数点
- 乗算は `((a * b) / 65536) | 0`。**`>> 16` は 32bit 切り詰めのため使用不可**
- `Math.random` / `Date.now` / `performance.now` 禁止
- `Math.sqrt` / `sin` / `cos` / `pow` 等の浮動小数点関数 禁止（`Math.imul` / `Math.abs` は可）
- 乱数は単一 seed の xorshift32 のみ
- `Map` / `Set` / `for...in` のイテレーション順に依存しない
- 場の更新はダブルバッファ方式
- 固定タイムステップ（3600ステップ）
- 平方根が必要な場合は `isqrt`（ビット単位法・厳密値）を使う

**検証手段**: `scripts/check-forbidden-apis.js`（`src/` 限定）と
`scripts/check-runtime-hashes.js`。CI で Node 20/22 マトリクス実行。

### 2-3. 指標と基準

| 決定 | 理由 |
|---|---|
| 基準2・3 の判定指標は **completionRatio**（生値の整数比） | `completionStep` は崖端指標。3%変位で10件中8件が未到達となり測定が成立しなかった |
| 基準3 は 1% / 3% / 10% の3水準。単調性 + 10%が1%の3.0倍以上 | 旧定義（10%で15%以上変化）は偽陽性。1%で13.4%、10%で15%＝ノイズ床を測っていた |
| 基準2 は9/10以上がPASS。Step 4の報告では数値のみで合否判定が抜けていた | adv:diff = 1:1 は9/10でPASS |
| adv:diff = 1:1 は基準1・2・3がPASSし、基準4のみFAIL | occupiedPeakは4,037〜4,090で、数値基準が最も通る領域に見るべき流れが存在しない |
| `densityMax` は輻輳指標として使わない | 総流出予算が density 比例のため、source 密度は下流に依存しない source 平衡値である |
| 輻輳指標は `densityMaxExSource`（全sourceセルと各マンハッタン距離1近傍の和集合を除外） | — |
| `completionAuc` は導入しない | completionRatio が平坦でなかったため、保険を使う条件が成立しなかった |
| **基準の閾値は変更しない** | 基準を通すための調整を構造的に禁じる |
| 掃引ハーネスは判定・順位付け・推奨を行わない | 自動探索が基準を通す方向に走ると、上記の禁止が機械的に破られる |
| 長い迂回経路の崩壊原因は、guideが線方向のみで線へ戻る成分を持たないこと | Step 7でdetourはギャップ通過後に場外へ散った。ギャップ幅・流量上限ではなく経路長耐性の問題として扱う |
| Node 22 の決定性確認は CI の Node 20/22 マトリクスに任せ、ローカルは Node 20 のゼロ依存構成を維持する | CI が毎 push 実行するため、ローカル固定Nodeが短縮するのは取得待ちのみ。一方で依存追加は Vanilla JS・ビルド工程なし・外部ライブラリ不可という前提を損なう |

### 2-4. 実装方針

| 決定 | 理由 |
|---|---|
| `measure: true` 分岐内に限り計装を追加してよい | measure=false/true でハッシュが一致することを実測済み。「src/ を変更しない」制約はハッシュ不変を守る手段であって目的ではない |
| `maxStagnation` の定義は変更しない | 実験の途中で既存指標の意味を変えない。流量上限の効果は `fluxLimitedAmount` で見る |
| 微細最適化は実施しない | GC 4.62%、neighborIndex 0.17%。全施策を積んでも3〜4割。並列化は8〜10倍でモデルに触れない |
| engineVersion を上げたら同一コミットで `runtime-hashes.json` に記録 | 記録がなければ CI が FAIL する（Step 0.4 でゲート強化済み） |
| 1周1変更 | 原因帰属のため。clamp 修正と流量上限を同時に入れると効果を切り分けられない |
| `poc-1-wide` の既定はsource幅1・sink幅5 | source幅9は線3本のため注入の67%が無誘導。sink幅1は正常なビーム移動を当たり／外れに二値化した。基準値から独立に確認された構造的欠陥を除去し、sink幅は後で狭められる安全側の5とした |
| 線は障害物セルにも通常どおり焼き込む | 障害物セルのguideは移送で参照されない。焼き込みを除外して障害物の縁に新しい不連続を作る必要がない |
| 線を純粋なポテンシャル場へ全面置換せず、既存guideへ障害物を越えない距離場の復元力を加算する | 全面置換案では旧挙動を機械的に証明できない。`restoreWeight=0` で0.7.0の全9ハッシュを保存したまま、線から外れた材料だけを戻せる |
| guide の定式化は復元力の加算方式で決着とする | Step 8で静的BFS距離場の最急降下方向を既存guideへ加算し、障害物を越える復元を避けつつ後方互換を証明できた |
| 混雑基準は `congestionReference` としてcapacityから分離し、通気度はadvectionScoreだけへ乗算する | capacityとreverseThresholdの依存を崩さず、diffusionによる混雑回避を残す |
| 密度場スナップショットを掃引成果物としてcommitする | 掃引CSVはスカラーのみのため、数値の64×64密度場も保存する |
| 通気度（Step 9）は残す | 自己調整は戻らなかったが、中央ルート比率の絶対値を28.0%→33.6%と動かし、完了率・場外損失を悪化させない |
| 漏れ防止は「力」ではなく「幾何制約」で担う | 復元力は漏れと自己調整の両方を同時に止める。制約なら経路選択の自由度を奪わない |
| 回廊制約は restoreWeight = 0 のときのみ機能する | 復元力が非ゼロだと材料が線を離れず、回廊が発動しない。掃引の対照群で cw=2・rw=Q/16 が Step 9 と同じ 0.12/0.17pt に留まることを確認 |

## 4. 保留中の判断

### Step 10 更新

`corridorWidth`・`restoreWeight`・混雑設定の既定値、回廊縁の扱い、中央ルート比率の妥当性、下流混雑ポテンシャル、非線形圧力は保留する。g=63ではblockedが空になるため、回廊幅だけを他レイアウトの場外損失根拠にしない。

| 論点 | 現状 | いつ判断するか |
|---|---|---|
| **基準4 の指標セット** | 均質場では達成不能だったが、峡谷g=1・edgeFluxMax 128/256でdistributedがtotalCompleted最大となり基準4がPASSした。detourがstraightを上回る構成はなかった | Step 7レビュー。**指標セットは単独で緩めないこと** |
| **基準2 の閾値5%** | 太い雲は摂動に鈍く、細いビームは敏感。0.5.0 で 6/10 → 3/10 になったのは劣化ではなく流れが生まれた副作用。coherent な流れと手ぶれ耐性は原理的にトレードオフ | 流れの形が確定してから |
| **基準2 の高誘導域での失敗要因** | **推定（未検証）**：幅1セルの sink が、ビームの微小な移動を「当たり／外れ」の二値に変換していること。線を1%動かせばビームも1%動くのは正常な応答であり、問題は的の幅にある。**Step 5 で検証を試みたが、シナリオ欠陥により測定不成立（第3-4節）。仮説は棄却されていない** | Step 6 の source 幅1 × sink 幅掃引 |
| **capacity / reverseThreshold** | capacity = 262,144 は観測 densityMax の約60倍で過大。ただし **下げるのは狭窄部を作った後**。候補（16,384 / 32,768 / 65,536）はいずれも reverseThreshold = 196,608 を下回り、逆流が原理的に発火不能になる | 狭窄部導入後。両者を同時に変更しないこと |
| **source / sink の多セル化** | 0.7.0で既定をsource幅1・sink幅5へ変更。Step 6 CSVの3ハッシュと一致 | 必要ならゲーム設計判断としてsinkを狭める別Issueを起票 |
| **障害物・狭窄部の導入** | 0.7.0で縦壁と中央・迂回ギャップを導入。g=1の全edgeFluxMaxとg=3の128/256で直進の`densityMaxExSource`がx=31に現れた | Step 7レビュー |

### 5-3. source の流出律速（0.4.0 / 0.5.0 共通）

`injectionPerStep` = 1,024 に対し、source の実効流出は
`4 × edgeFluxMax` で頭打ちになる。

| edgeFluxMax | 実効流出/step | 判定 |
|---:|---:|---|
| 128 | 510.99 | 注入を捌けない |
| 256 | 1,019.9 | ほぼ同水準（実質不足） |
| 512以上 | 1,038〜1,272 | 律速しない |

**128/256 で観測される滞留・逆流・capacity クランプは、すべて
source セル単独の現象であり、経路の詰まりではない。**
