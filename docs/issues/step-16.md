# Step 16: 線からの距離別の密度分布を計測する

## 0. 位置づけ

この企画の狙いの一つは「**少ない入力から、想像以上の結果が返ってくる**」である。
Step 12〜14 でビューアを整えた結果、実際に触った評価として
「線を引いて、なんとなく**想像通りに**液体が動いている手応え」が得られている。

**しかし「想像通りに動いたか」＝「材料が引いた線に沿って流れたか」を測る量が存在しない。**

### `coherenceLength` は代替にならない

外部意見として3件、いずれも `coherenceLength` を線の可読性の指標として使う案が
出たが、実測で否定済みである（Step 14 で撤回として記録）。

- 掃引144行で **6値（8 / 9 / 13 / 14 / 33 / 63）しか取らず**、106行が 63 に張り付く
- 線が最も判別できる `corridorWidth` 1〜2 の straight 入力で **9〜33 に落ちる**
- 束の長さ（＝材料がどこまで到達したか）を測っており、線との一致ではない

### `occupiedCellsPeak` も代替にならない

入力により基準量が2〜3倍違う（straight の `corridorWidth=8` が 1,303、distributed の
`corridorWidth=3` が 1,260）。**最も無価値な画面を弾けない。**

engineVersion: **0.11.0 のまま（変更しない）**

前提: PR #25（Step 15）がマージ済みであること。

---

## 1. 方針：スカラーではなく分布を記録する

**単一の「一致度」をエンジンに計算させないこと。**

理由は2つある。

### 1-1. 「距離 d 以内の割合」は構造上ほぼ 100% になる

回廊制約（Step 10）は、材料を線から `corridorWidth` 以内に閉じ込めている。
したがって `d >= corridorWidth` の割合を測ると**定義上ほぼ 100% となり、何も測れない。**
`d` の選び方が結論を決めてしまう。

### 1-2. 定義は分布を見てから決められる

距離ごとの密度合計を記録しておけば、「一致度」の定義を変えても**再実行が不要**である。
掃引ハーネスが判定・順位付け・推奨を行わないのと同じ原則を、計測にも適用する。

**エンジンは分布を記録するだけとし、比・平均・判定は行わないこと。**

## 2. 実装内容

### 2-1. 既存の距離場を再利用すること

Step 8 で導入し、Step 10・11 で回廊判定に使っている BFS 距離場をそのまま使う。

```js
const { distance } = buildRestoreField(lineMask, blockedMask, config);
```

- `distance === 0` は線上のセル
- `distance === -1` は障害物、または線から到達できないセル
- 実測では `poc-2-canyon` / `distributed` で最大 32、距離0が 602セル、以降なだらかに減少

**新しい場を作らないこと。既存の計算結果を再利用すること。**

### 2-2. 追加する計測（measure 専用）

| 名前 | 内容 |
|---|---|
| `lineDistanceDensity` | 長さ 65 の配列。添字 `d` に、`distance === d` のセルの**最終密度の合計**。`d >= 64` は添字 64 にまとめる |
| `lineDistanceCells` | 長さ 65 の配列。添字 `d` のセル数（密度によらない静的な値） |
| `lineDistanceUnreachable` | `distance === -1` のセルにある密度の合計 |
| `lineDistanceUnreachableCells` | `distance === -1` のセル数 |

- **すべて生の合計値とし、比や割合に加工しないこと**
- `measure = false` のときは計算しないこと
- `lineDistanceCells` は静的だが、利用側で正規化するために必要なので記録すること
- **`lineDistanceUnreachable` は 0 になるはずである**（障害物セルに材料は入らない）。
  **0 でない場合はそのまま報告すること。定数で辻褄を合わせないこと**

### 2-3. 時系列には含めないこと

Step 15 の `timeline` に含めると 1標本あたり 130 個の数値が増え、CSV が扱えなくなる。
**本 Step では最終状態のみとする。** 時間変化が必要になれば別 Step で扱う。

### 2-4. 掃引 CSV には含めないこと

列数が爆発する。**`scripts/sweep.js` の CSV 列構成を変更しないこと。**

### 2-5. ビューアでの表示（`debug/`）

Step 14 で定めた境界線（`runSimulation` の入力を作る／出力を読む、まで）の内側である。

- `lineDistanceDensity` と `lineDistanceCells` を**表形式で表示**すること
  （距離 0 から、密度合計が 0 になる最初の距離まで。以降は省略してよい）
- **CSV としてダウンロード**できること
- `lineDistanceUnreachable` が 0 でない場合は警告として表示すること
- **グラフ描画は行わない。** 表と CSV のみとする

## 7. 想定される結果

- `corridorWidth = 1` では距離 2 以上の密度が 0 になると予想する
- `corridorWidth = 8` では距離 8 まで密度が分布し、距離 9 以上が 0 になると予想する
- 既定（無制限）では距離 20 以上まで密度が広がると予想する
- `lineDistanceUnreachable` は全件 0 になると予想する
- 距離 0（線上）の密度が最も高くなると予想する。**ただし `corridorWidth` が大きい構成
  では、距離 0 が最大にならない可能性がある**
- `lineDistanceDensity` の総和は、場に残っている量と一致すると予想する

**いずれも外れて構わない。外れた場合に定数や添字範囲を調整して辻褄を合わせないこと。
未達は未達のまま報告すること。**

## 8. `docs/DECISIONS.md` の更新（必須）

### 8-1. 第2節「有効な決定」へ追加

| 決定 | 理由 |
|---|---|
| 「線と流路の一致度」はスカラーではなく、線からの距離別の密度分布として記録する | 回廊制約が材料を `corridorWidth` 以内に閉じ込めているため、「距離 d 以内の割合」は `d >= corridorWidth` で構造上ほぼ 100% になり、`d` の選び方が結論を決めてしまう。分布であれば定義を変えても再実行が不要 |
| 分布の記録に既存の BFS 距離場を再利用し、新しい場を作らない | Step 8 で導入し Step 10・11 で回廊判定に使っている距離場をそのまま使える。新しい概念を持ち込まない |
| 計測はスカラーへの加工・判定・比の算出を行わない | 掃引ハーネスが判定・順位付け・推奨を行わないのと同じ原則。加工は利用側で行う |

### 8-2. 第4節「保留中の判断」の更新

既存の保留項目はそのまま残すこと。以下を更新する。

- **「一致度」をどう定義するか**（本 Step で分布は取れる。スカラー化するか、
  するならどう定義するかは、分布を見てから決める）
- **シンクごとの到達量と到達時刻を計測するか**（次 Step の候補。`gaps` と同型で
  実現でき、`timeline` にも載せられる）
- **「時間を稼ぐ」ことに価値を持たせるか**（実装は不要。Step 15 の時系列で検証できる。
  成功・失敗の型の判断に含まれる）
- **決壊の3案**（有限の供給／圧力依存の通過容量／壊れる障害物。いずれもモデルの
  定式化の変更。**基本線を優先し、後回しとする**）
