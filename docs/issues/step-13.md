# Step 13: ビューアの線描画を自由化する

## 0. 位置づけ

Step 12 でビューアを現行エンジンに追随させ、任意の線を引けるようにした。
その結果、**「見て面白いか」に初めて肯定的な判断が得られた**（第8-1節に記録する）。

同時に、線の引き方について2点の不足が挙がった。

| 指摘 | 現在の実装 |
|---|---|
| 描き方：なぞって描けない | `debug/viewer.js` がクリックで制御点を1点ずつ置く方式 |
| 経路の形：曲線にできない | 上と同じ。制御点が少ないため折れ線に見える |

### 調査結果：どちらも `src/` の制約ではない

`src/lines.js` の `burnLines` を確認したところ、**制御点数に上限がない。**

```js
if (!Array.isArray(points) || points.length < 2) {
  throw new RangeError("each line needs at least two control points");
}
```

さらに各セグメントは **1/4セル刻み**でサンプリングされる。

```js
const samples = ((extent + (Q >> 2) - 1) / (Q >> 2)) | 0;
```

したがって、**制御点をセルより細かく置けば、エンジンから見て折れ線と曲線の区別は
つかない。** また `assertPoint` は Q16.16 の範囲検査のみで整数セルを要求していない
ため、**サブセル座標も元から通る。**

実測（制御点161個の正弦波3本、`poc-2-canyon` / `gapWidth=1` / `corridorWidth=2` /
`restoreWeight=0` / `corridorBlocksOutOfField=true`）:

```text
実行 3,639 ms   stateHash=d628a9ce
completionStep=-1  完了率44%  場外0%  残55%
gapThroughput central=1,782,979  detour=0
```

**プリセット（制御点3〜5個）の実行時間 約3.6秒と変わらない。** サンプリング数は
経路長で決まり、分割の細かさでは決まらないため、制御点を増やしても計算量はほぼ
増えない。

よって本 Step は **`debug/` の変更のみで完結する。**

engineVersion: **0.11.0 のまま（変更しない）**

前提: PR #19（Step 12）がマージ済みであること。

## 2. 実装内容

### 2-1. 内部座標を Q16.16 のまま保持する

現行の `qLinesToCells` / `cellLinesToQ` は Q で除算・乗算するだけで、
`validateLines` が整数セルを要求している。

```js
// debug/viewer.js（現行）
if (!Array.isArray(point) || point.length !== 2 || !point.every(Number.isInteger)) {
  throw new TypeError("control point coordinates must be integers");
}
```

**この整数制約を外し、線の内部表現を Q16.16 の整数に統一すること。**

- 範囲検査は `0 <= x < width * Q`、`0 <= y < height * Q` とする
- 描画時のみセル座標へ換算する
- `src/lines.js` の `assertPoint` と同じ条件になるようにする（再実装せず、
  条件が一致していることを報告に書けばよい）

保存 JSON の `lines` も Q16.16 で持つこと。**`formatVersion` を 2 に上げ、
`formatVersion: 1`（セル単位）の JSON も読み込めるようにすること**（読み込み時に
Q を掛けて変換する）。過去に保存した盤面を開けなくしない。

### 2-2. ドラッグによる連続描画

現行のクリックで点を置く方式に加えて、**ポインタを押したまま動かすと制御点を
連続で拾うモード**を実装すること。

- 描画モードの切り替え（「点を置く」／「なぞる」）を UI に置く
- なぞるモードでは、ポインタを離した時点で1本の線が確定する
- 既存の「制御点のドラッグ移動」「末尾の制御点を取り消し」は残すこと
- 3〜5本・各2点以上の制約は現行どおり UI で強制すること

### 2-3. 制御点の間引き（閾値は切り替え可能にすること）

ドラッグで拾うと1ストロークが数百点になる。実行時間はほぼ増えないが、
**JSON と URL ハッシュが肥大する**（座標1点あたり20文字前後、3本×300点で約18KB）。

間引きを実装すること。ただし **間引きすぎると折れ線に戻り、絵が変わる。**

- 方式：直前に採用した点からの距離が閾値未満の点を捨てる（単純な距離間引き）
- **閾値を UI で切り替えられること。** 選択肢は
  `0（間引きなし）/ 0.25セル / 0.5セル / 1.0セル`
- **既定は 0.25セル**とする。理由はエンジンのサンプリング間隔が 1/4セルであり、
  それより細かい点は結果に寄与しないと推定されるため。**ただしこれは未検証の
  推定であり、既定値の決定ではない。** 第5節で実測を報告すること
- 間引きは「なぞる」モードで拾った点にのみ適用し、手で置いた点や
  ドラッグ移動した点には適用しないこと
- 現在の制御点数を UI に表示すること（線ごと、および合計）

### 2-4. URL と JSON の肥大対策

- **URL ハッシュが 8,000 文字を超える場合は、URL への反映を止めて警告を表示すること**
  （「制御点が多いため URL 共有できません。JSON で保存してください」等）。
  黙って壊れた URL を生成しないこと
- JSON ダウンロードには文字数制限を設けないこと
- 現在の URL 文字数を UI に表示すること

### 2-5. `steps` の上限

Step 12 のレビューで指摘された。`runSimulation` は同期実行のため、大きな `steps`
でタブが応答しなくなる（1step あたり約1.2ms、3,600step で約3〜4.5秒）。

- `#steps` に `max="20000"` を設定すること
- 上限を超えた場合はエラーメッセージを表示し、実行しないこと

## 3. 既知の制限として明記すること

以下は不具合ではないが、知らないと混乱するため `docs/reports/step-13.md` の
「既知の制限」と、可能なら UI 上にも書くこと。

### 3-1. 同じ形の線でも制御点数が違えば結果が変わる

`burnLines` は各セグメントで `sample = 0` と `sample = samples` の両方を
`addSample` に渡すため、**セグメントの接合部でサンプルが重複する。**

したがって、同じ形の線でも制御点3個で描いた場合と300個で描いた場合とで、
`stateHash` は一致しない。**間引き閾値を変えると結果が変わるのはこのためである。**

既存プリセットのハッシュには影響しない（プリセットは変更しないため）。

### 3-2. 線の本数は 3〜5 本

`src/lines.js` のハード制約であり、本 Step では変更しない。

### 3-3. 源とシンクの位置は固定

`poc-0-default` / `poc-2-canyon` は `(4,32)` と `(59,32)`。本 Step では変更しない。

## 8. `docs/DECISIONS.md` の更新

### 8-1. 第2節「有効な決定」へ追加

| 決定 | 理由 |
|---|---|
| **「見て面白いか」に初めて肯定的な判断が得られた** | Step 12 のビューアで実際に線を引いた結果、「今までになかった楽しさ」「流体シミュレータを自分で操作している感じ」「流れをコントロールしている感じ」との評価。Step 7 以降5回保留されていた論点に、数値基準ではなく操作体験によって初めて答えが出た |

## 9. 想定される結果

- ドラッグ描画1ストロークで制御点は数百個になると予想する
- 間引き閾値 0 と 0.25セルとで、`stateHash` は一致しないが密度場の見た目は
  ほぼ変わらないと予想する
- 間引き閾値 1.0セルでは折れ線に見えると予想する
- 実行時間は制御点数によらずほぼ一定（約3.5〜4.5秒）と予想する
- URL ハッシュは閾値 0 では 8,000 文字を超えると予想する

**いずれも外れて構わない。外れた場合に閾値や既定値を調整して辻褄を合わせないこと。
未達は未達のまま報告すること。**
