# Step 14: ビューアで盤面（障害物・源・シンク・ギャップ）を編集できるようにする

## 0. 位置づけ

Step 13 で線を自由に引けるようになった。次の制約は**盤面が3種類の固定配置しかない**ことである。

`runSimulation` は `source` / `sink` / `blocked` / `gaps` を**すべて引数で受け取る。**

```js
runSimulation({ lines, source, sink, blocked = [], gaps = [], seed, config })
```

固定されているのは `src/scenarios.js` の定数側だけである。

```js
export const SOURCE = freezeCells([[4, 32]]);
export const SINK   = freezeCells([[59, 32]]);
```

**つまり盤面の幾何は既にエンジンの自由な引数であり、`src/` を変更せずに任意の配置を
渡せる。** 柱、迷路、器の外周、非対称な壁、源やシンクの移動、いずれも可能である。
制約は「源とシンクが障害物と重ならないこと」だけである。

本 Step は `debug/` にその編集手段を用意する。**`src/` は一切変更しない。**

engineVersion: **0.11.0 のまま（変更しない）**

前提: PR #21（Step 13）がマージ済みであること。

## 1. 前提となる2つの決定（第9節で DECISIONS に記録する）

本 Step の作業前に、以下2件が決定された。実装はこれに従うこと。

### 1-1. PoC-0 の受け入れ基準の位置づけを限定する

受け入れ基準は現在 4件中2件 PASS で、Step 7 から動いていない。原因は既定値である。

```js
restoreWeight: 0                    // Step 8 の機構は既定では無効
congestionWeight: 0                 // Step 9 の機構は既定では無効
corridorWidth: width + height       // Step 10 の機構は既定では無効（無制限）
corridorBlocksOutOfField: false     // Step 11 の機構は既定では無効
```

既定値を決めるには「何が良いか」の基準が要り、その基準を決めるには遊んでみる必要が
あり、遊ぶには本 Step が要る、という循環が生じていた。

**決定：受け入れ基準4件は「エンジンが壊れていないことの確認」に位置づけを限定する。
PoC-0 の通過条件としては扱わない。**

根拠：決定論は Node 3系統とブラウザで一致、保存則は全掃引点で成立、300点以上の掃引で
依存関係が記録済み。エンジンの健全性は別途確認できている。また基準2・4 の指標側に
複数の欠陥が判明している（中央ルート比率は straight / detour で構造上固定、
`gapWidth=63` は障害物が生成されない、`coherenceLength` は144行で6値しか取らない）。
**欠陥のある物差しに合わせて既定値を選ぶことを避ける。**

**基準の閾値は変更しない。既定値も変更しない。位置づけのみを変える。**

### 1-2. `debug/` は診断用のままとする

`debug/` は Step 12 で全パラメータ操作、Step 13 で自由描画を得た。このまま機能を
足し続けると、未決定である製品の描画スタックがなし崩しに決まる。

**決定：`debug/` は診断用ツールのままとする。ゲーム層（上物）は将来、別ディレクトリに
新規で作る。**

境界線を次のとおり定める。**本 Step 以降、この線を越える変更を `debug/` に入れない。**

| `debug/` に入れてよい | `debug/` に入れてはいけない |
|---|---|
| `runSimulation` の**入力を作る**もの（線、パラメータ、盤面幾何、乱数種） | 成功・失敗の判定、スコア、ランキング |
| `runSimulation` の**出力を読む**もの（計測値の表示、密度の描画、再生、保存） | 演出、色設計、効果音、アニメーション表現 |
| 再現・共有のための保存形式 | ステージ進行、チュートリアル、UI の作り込み |

**盤面編集は「入力を作る」側なので、この線の内側である。**

## 3. 実装内容

### 3-1. 障害物の編集

- セルをクリックで障害物のオン／オフを切り替える
- ドラッグで連続して塗る／消す（塗りと消しはモードで切り替える）
- 矩形選択で一括の塗り／消し
- 全消去
- 現在の障害物セル数を表示する

### 3-2. 源とシンクの編集

- 源・シンクとも**複数セルを許す**（`createWideSink(5)` が実際に5セルを渡している）
- セルを選んで源に指定／シンクに指定／解除
- **`docs/LOOP.md` の「source / sink の多セル規則」に従い、座標配列は昇順に固定して
  保存すること。実行時にソートしない**
- 源・シンクとも最低1セル必要

### 3-3. ギャップの定義

`gapThroughput` は `gaps`（名前付きのセル群）が渡されていないと計測されない。
盤面を自由に作れるようにしても、経路の観測ができなければ価値が半減する。

- 開いているセルを選び、**名前付きのギャップ群として登録**できること
- **群は最大4つまで**。名前は編集可能（既定は `A` / `B` / `C` / `D`）
- `src/simulation.js` の `createGapMap` は**障害物セルをギャップに含めることを拒否する**。
  UI 側で先に弾き、理由を表示すること
- ギャップ未定義でも実行できること（`gapThroughput` は `—` と表示）

### 3-4. 妥当性の検証

実行前に以下を UI で検証し、満たさない場合は実行ボタンを無効化して理由を表示すること。
`src/` 側の例外に頼らず、先に弾くこと。

- 源・シンクが障害物と重なっていない
- 源・シンクがそれぞれ1セル以上
- ギャップセルが障害物と重なっていない
- ギャップセルに重複がない
- 障害物セルに重複がない
- すべてのセルが場の範囲内

### 3-5. プリセットと「検証用シナリオ」の区別

- 既存の3シナリオ（`poc-0-default` / `poc-1-wide` / `poc-2-canyon` ＋ `gapWidth`）は
  **プリセットとして残し、編集の出発点として読み込めること**
- 編集を加えた時点で `scenarioId` を **`custom`** に変えること
- **`custom` の盤面はハッシュ回帰テストの対象外である。** その旨を UI に常時表示すること
  （例：「編集中の盤面は検証対象外です」）
- プリセットを未編集のまま実行した場合は、`scenarioId` を保ったままとし、
  `runtime-hashes.json` と一致することを確認できること

### 3-6. 保存・読み込み・URL

- 保存 JSON に盤面（`blocked` / `source` / `sink` / `gaps` / `scenarioId`）を含める。
  **`formatVersion` を 3 に上げること**
- **`formatVersion` 1 と 2 の JSON も読み込めること。** 盤面が無い場合は
  `scenarioId` と `gapWidth` からプリセットを復元する
- URL ハッシュは Step 13 で 8,000 文字制限を設けている。**盤面が加わると超える場合が
  ある。超えたときは Step 13 と同じ扱い（URL 反映を止め、警告を出し、共有ボタンを
  無効化）とすること。黙って壊れた URL を生成しないこと**
- 障害物の座標をそのまま並べると肥大するため、**保存形式は任意に圧縮してよい**
  （連長圧縮など）。ただし読み込み側で完全に復元できること

### 3-7. 表示

- 障害物、源、シンク、ギャップ群を、それぞれ区別できる色で描くこと
- ギャップ群は名前を表示すること
- 既存のオーバーレイ切り替え（障害物 / 線 / 回廊の縁 / 場の縁）は維持すること

## 8. 想定される結果

- 障害物を自由に置いた盤面では、源からシンクへ到達できない配置も作れる。
  **その場合 `completionRatio` が 0% になるのは正しい挙動であり、修正しないこと**
- 器の形にした盤面では `outOfFieldRatio` が 0% になると予想する（外周が障害物のため）
- 柱の盤面では `blockedFrontDensityMax` が柱の手前を指すと予想する
- 障害物で囲まれて線から到達できないセルが生じた場合、Step 10 で導入した回廊判定は
  それを回廊外として扱う（`distance === -1`）。**既定の `corridorWidth` は無制限なので
  影響は出ないと予想するが、確認すること**
- 保存 JSON は障害物の数に応じて肥大し、器の盤面では URL の 8,000 文字を超えると
  予想する

**いずれも外れて構わない。外れた場合に定数や既定値を調整して辻褄を合わせないこと。**

### 9-2. 第3節「撤回・棄却された主張」へ追加

| 主張 | 撤回理由 |
|---|---|
| Claude の「ステージという概念を導入するかどうかを決める必要がある」 | 盤面の幾何は既に `runSimulation` の自由な引数であり、導入の判断は不要だった。実際に決める必要があったのは、検証用シナリオとプレイ用盤面の分離という運用の問題のみ |
| 外部案「`coherenceLength` を合否の足切りに使う」（3つのAIが共通で提案） | 掃引144行で6値（8/9/13/14/33/63）しか取らず、106行が63に張り付く。さらに線が最も判別できる幅1〜2の straight 入力で 9〜33 に落ちる。線の可読性ではなく到達距離を測っている |
| 外部案「`occupiedCellsPeak` の絶対値を足切りに使う」（1,200 / 1,400 の提案） | 入力により基準量が2〜3倍違う。straight の幅8（1,303）が distributed の幅3（1,260）より小さく、最も無価値な画面を弾けない。使うなら線の長さに対する比が要る |

### 9-3. 第4節「保留中の判断」の更新

既存の保留項目は**そのまま残すこと。** 以下を追加する。

- **成功・失敗の型**（配分型／期限型／詰まり解消型が候補として挙がっている。決定は
  盤面編集で遊んでから）
- **「時間を稼ぐ」ことに価値を持たせるか**（現在の計測はすべて総量か最終状態で、
  時間帯ごとの通過量が取れない。検証には計測の追加が要る）
- **「線と実際の流路の一致度」の計測を追加するか**（「想像通りに動いた」を測る量が
  現在存在しない。`coherenceLength` は代替にならないことが 9-2 で確定した）
- **傾斜（重力に相当する項）を導入するか**（モデルの定式化の変更。既定0で後方互換に
  できるが、「線に沿って流れる」との競合が未知）
- **順番（複数シンクへの到達順）を導入するか**（現在シンクは到達量が合算され区別
  されない。`gapThroughput` と同型の仕組みが要る）
- **対戦を導入するか**（材料に所有者の区別が無く、移流・拡散・混雑のすべてに影響する。
  主軸には置かない。決定論とリプレイがあるため非同期対戦なら盤面交換のみで成立しうる）
- **ゲーム層を置く新規ディレクトリの名前**（本 Step では作らない）
