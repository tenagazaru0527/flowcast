# Step 18: ゲーム層を1周だけ作る（課題・判定・スコア軸）

## 0. 位置づけ

**Step 1〜17 は、すべて土台である。ゲームの部分に一度も着手していない。**

| Step | 内容 | 種別 |
|---|---|---|
| 1〜6 | 流体の基礎 | エンジン |
| 7〜11 | 線に沿う／混雑を避けるの両立 | エンジン |
| 12〜14 | 見る・触る道具 | ツール |
| 15〜17 | 測る道具 | ツール |

### 現状の診断

ゲームに必要な5つが、**1つも存在しない。**

| 必要なもの | 現状 |
|---|---|
| 目標 | 無い |
| 制約 | 弱い（線3〜5本だが、どう引いても大体流れる） |
| 失敗 | 無い（どの線でも結果は出る） |
| 上達 | 測れない（何が上手いのか定義が無い） |
| 意外性 | 無い |

開発者本人の評価も「確認を重ねるにつれて真新しさや違いがわからなくなってきた」である。

### 実測が示していること

- Step 16 の距離分布：材料は線から離れても薄くならない
  （`corridorWidth=8` で距離0が647、距離8が570。**12%しか減らない**）。
  線は「どこを埋めるかの指定」であって、流れの質を決めていない
- Step 15 の時系列：`gapWidth=1` では step 300 で区間通過量が 512 に張り付き、
  **3,300ステップ何も変わらない**

**見続けても新しいことが起きないのは、実際に何も起きていないためである。**

### 先例調査から得た方針

流体を扱う既存作は2つに分かれる。

- **おもちゃ型**（The Powder Toy、Powder Game、各種 Fluid Simulation）：
  目標も失敗も無い。触ると気持ちよいが飽きる。**現在の flowcast はここにいる**
- **舞台型**（Noita）：流体は世界の性質で、遊びの中心ではない

一方、市場で成立している「液体パズル」（Water Sort、Happy Glass 等）は
**流体計算ではない。** 目標の明快さで成立している。

構造として最も近いのは Zachtronics の Opus Magnum である。

- 課題が明示される
- どんな動く解でも先に進める
- **クリア後に複数の軸で競う**（時間・コスト・面積）
- 解を他人と比較できる

**flowcast の強みは流体の忠実さではなく、決定論とリプレイである。**
Node 3系統とブラウザで1ビット一致し、線の座標だけで完全再現できる。
これは Opus Magnum 型のリーダーボードと同じ性質であり、17 Step かけて既に完成している。

**本 Step は、この構造を1周だけ作って「面白いかを確かめる」ことを目的とする。
完成品を目指さない。面白くなければ捨てる。**

engineVersion: **0.11.0 のまま（変更しない）**

前提: PR #29（Step 17）がマージ済みであること。

## 2. 作るもの

### 2-1. 課題（1つだけ）

**配分型**とする。Step 17 で `sinkThroughput` が取れるようになったばかりであり、
「時間の概念が出る」流体の性質と組み合わせやすいため。

課題は `game/` 内の JSON として定義する。**本 Step では1つだけ作る。**

```text
盤面   : Step 14 の multisink 盤面を出発点とする（障害物・源・シンク・ギャップは流用）
シンク : upper = [[59,20]], lower = [[59,44]]
目標   : upper に到達量全体の 55〜65%、lower に 35〜45% を届ける
制約   : 場外損失 0%、到達率 50% 以上
設定   : corridorWidth=2, corridorBlocksOutOfField=true, restoreWeight=0,
         congestionWeight=0, congestionReference=2048, edgeFluxMax=512,
         steps=3600, sampleInterval=100
```

**この目標値は暫定である。** Step 17 の実測では同盤面が 69:31 だった。
55〜65% は「そのままでは達成できず、線を変える必要がある」帯として置いている。
**達成不可能だと判明した場合は、値を変えず、達成不可能だったと報告すること。**

### 2-2. 判定（順序付き。合算スコアにしないこと）

**必ず次の順序で判定し、前段を通らなければ後段を評価しないこと。**

1. **制約**：場外損失 0% かつ 到達率 50% 以上 → 満たさなければ **失敗**
2. **目標**：upper の比率が 55〜65% → 満たさなければ **失敗**
3. 両方満たせば **クリア**

**重み付き合算スコアを作らないこと。** 過去2回、単一量の最大化で
「基準を最もよく満たす設定が画面として最も無価値」になっている。

### 2-3. スコア軸（クリア後に表示。順位付けはしない）

クリアした場合のみ、次の4軸を**並べて表示する。合算しないこと。**

| 軸 | 計測 | 意味 |
|---|---|---|
| 速さ | `sinkFirstArrivalStep` の遅い方 | 両方のシンクに届くまで |
| 量 | `totalCompleted` | どれだけ運べたか |
| 集中 | `lineDistanceDensity[0]` ÷ 全距離の合計 | 線の上にどれだけ乗ったか |
| 手数 | 線の本数と制御点の合計 | 単純な解ほど小さい |

- **すべて生の数値を並べるだけとし、良し悪しの判定・順位付け・星の数などを
  付けないこと**
- 「集中」は Step 16 の実測で `corridorWidth` により 77.6% / 61.5% / 30.5% / 21.0% と
  変化することが確認されている

### 2-4. 画面

最低限でよい。**演出・色設計・アニメーション表現は行わないこと。**

- 盤面と線の描画（`debug/` のコードを参考にしてよいが、`debug/` を変更しないこと）
- 線を引く（なぞり描画。3〜5本、Step 13 と同じ制約）
- 実行ボタン
- 密度場の表示（最終状態のみでよい。再生は本 Step では不要）
- 判定結果（クリア／失敗と、失敗ならどの条件で落ちたか）
- クリア時のみ第2-3節の4軸
- **やり直しボタン**

### 2-5. 失敗理由の提示

**「失敗」の一言で終えないこと。** どの条件で落ちたかを示すこと。

```text
例：
  場外損失 12%（0% が必要）
  到達率 63%（50% 以上：満たしている）
  upper 比率 71%（55〜65% が必要）
```

**「次に線をどう変えるか」が想像できる形にすること。** 数値の提示のみとし、
助言や誘導の文言は入れないこと。

### 2-6. 解の保存

- クリア・失敗にかかわらず、線と結果を JSON で保存・読み込みできること
- 形式は `debug/` の `formatVersion: 4` と互換にしてよいが、
  **`debug/` のコードを共有せず、`game/` 内に独立して持つこと**
  （`debug/` を変更しないため）
- **`stateHash` を必ず含めること。** 決定論の検証と、将来の解の比較に使う

## 4. 動作確認として行うこと

**課題が「そのままでは達成できず、線を変えれば達成できる」ものになっているかを
確かめること。**

- Step 14 の multisink 盤面の線をそのまま使って実行し、判定結果を記録する
  （Step 17 の実測では upper 69% で、目標帯 55〜65% の外）
- **線を変えてクリアを試み、クリアできた解を1件コミットすること**
  （`docs/reports/data/step-18-solution.json`）
- **3回試してもクリアできない場合は、達成不可能だった可能性としてそのまま
  報告すること。目標値を変えないこと**

## 7. 想定される結果

- Step 14 の元の線では、upper 比率が目標帯を外れて**失敗**すると予想する
- 線を変えれば目標帯に入れられると予想する。**入れられない場合はそのまま報告すること**
- 「集中」の軸は `corridorWidth=2` 固定のため、線の引き方によって 50〜70% の範囲に
  収まると予想する
- 4軸のうち「速さ」と「量」は同時に良くできず、トレードオフになると予想する

**いずれも外れて構わない。外れた場合に目標値・制約・軸を調整して辻褄を
合わせないこと。未達は未達のまま報告すること。**

**本 Step の目的は課題を成立させることではなく、この形が面白いかを確かめる
材料を作ることである。**
